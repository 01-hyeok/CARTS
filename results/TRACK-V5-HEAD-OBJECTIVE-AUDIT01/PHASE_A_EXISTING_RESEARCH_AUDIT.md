## Answers to the audit questions (section 4)

1. **KL Gradient to each head**: `kl_per_head` (`utils/expert_head_metrics.py`) computes `KL(p_T || p_h)` PER (query, head) as an un-reduced `[B,S]` tensor -- so a per-head KL value always EXISTS as an intermediate; the question is only which reduction/weighting reaches the actual `.backward()` call. In canonical V5's own trainer (`train_v_sharedtop100_01.py::eval_channel` -> training loop), the loss backpropagated is `KL(p_T || p_bar)` where `p_bar = mean_h(p_h)` -- the per-head KL values are never separately computed or weighted inside V5's own training loop at all (confirmed by reading `eval_channel`: it builds `p_bar` directly via `torch.softmax(...).mean(dim=1)`, never materializes per-head KL). Each head's embedding receives gradient only through its contribution to the MEAN of the 5 softmax distributions -- diffused, not direct.
2. **Mean-Mixture Loss vs per-head KL Loss**: Mean-Mixture pools the 5 softmax PROBABILITY distributions first (`p_bar = mean_h p_h`), then takes one KL against the teacher. Per-head KL (`expert_weighted_loss`/`hard_expert_loss`) instead computes KL **separately for every head against the SAME teacher**, then combines the 5 scalars (`sum_h r_h * KL_h` for Soft, `KL_{h*}` only for Hard). Mathematically, `KL(p_T||mean_h p_h) != mean_h KL(p_T||p_h)` in general (KL's convexity in its second argument makes the mixture's KL <= average of the per-head KLs, Jensen) -- Mean-Mixture is a strictly looser, averaged-first objective; this is exactly the quantity PHASE F is asked to measure the GRADIENT consequence of.
3. **Soft Expert's per-head loss**: `expert_weighted_loss(responsibility, kl_vals) = mean_q[sum_h r_h(q) KL_h(q)]`, `r_h = softmax(-z(U_h)/tau_E)` (detached, a z-scored-then-softmaxed assignment weight over the 5 heads' own standalone future-MSE, never backprop'd through the assignment itself).
4. **Hard Expert's head-selection criterion**: `h*(q) = argmin_h U_h(q)` (detached), where `U_h(q)` = mean future-MSE of head h's own standalone Top-10 within the pool; only that one winning head's KL term gets gradient (`hard_expert_loss`).
5. **Existing head overlap / RetMSE/AggMSE**: YES, see the CRITICAL FINDING above -- already computed for V5 at all 4 target cells, from the canonical checkpoint, at the Mean-Mixture-selected epoch.
6. **J3's D/C vs this track's Head-level D/C**: J3 decomposes the error of ONE retrieval SET (5-head Mean-Mixture Top-10, a single set of 10 candidates) into within-set candidate-pair interactions. This track's PHASE C decomposes each HEAD's OWN independent Top-10 (5 different sets of 10 candidates, one per head) the same way, and PHASE D goes further to look at interactions BETWEEN heads' predictions (not within one head's own set). Same mathematical identity (`Agg=D+C`), different object being decomposed (one shared set vs. 5 independent per-head sets, vs. cross-head interactions).
7. **K/M's Aggregate Loss vs V5's Mean-Mixture Loss**: K2/M's aggregate loss is an EXPLICIT differentiable relaxation of the FINAL aggregate MSE (`MSE(R_soft, Y_q)` or a soft-top-K proxy of it), added as a direct training signal. V5's Mean-Mixture loss is pure KL-to-teacher on the AVERAGED PROBABILITY DISTRIBUTION -- it never directly supervises the aggregate prediction `R_mix` or its MSE at all. This is precisely the gap PHASE G's "L3 Aggregate-aligned Loss" candidate is asking whether to close.
8. **SoftTopK vs Hard Top-10, prior findings**: K2's own soft (training-time relaxation) vs hard (actual inference) AggMSE gap was 0.504919 vs 0.546943 (+7.7% relative, hard worse) -- a real, non-negligible, recurring gap. `EXP-SET-LOSS01`/`TRACK-A-SET-LOSS-CONTROL02`'s SRM/SoftCE Stage1-to-Stage2 transfer was inconsistent (val/test rank disagreement; only on-policy prefix meaningfully helped, and only at some cells). General lesson for this track's PHASE G: expect a real soft/hard gap to exist, and expect Stage1-metric improvement to be an unreliable Stage2 predictor independent of which relaxation is used.
9. **Reusable metrics**: Yes -- see CRITICAL FINDING. PHASE C's V5 row is a direct transcription for all 4 cells; `oracle_vs_fixed.json` partially answers PHASE E's single-head-oracle question.
10. **Metrics needing new computation**: Head-level error complementarity (PHASE D), full 31-subset Head Oracle (PHASE E2/E3), frozen-checkpoint gradient diagnostic comparing Mean-Mixture-KL vs per-head-KL (PHASE F), and Mean-Mixture-specific soft/hard alignment (PHASE G). All four require only the existing V5 checkpoint + existing Shared-P100 pool caches + CPU/GPU forward+backward passes -- no new training.

## Distinguishing this track's "Head Complementarity" from prior "Candidate Complementarity"

Explicitly flagged per the spec's own instruction (section 4, closing paragraph): TRACK-J3/K/M all study complementarity **between the individual retrieved candidates that end up inside one selected Top-10 set** (candidate-level, single retrieval mechanism). This track's PHASE D studies complementarity **between the 5 heads' own independently-produced aggregate predictions** (head-level, 5 parallel retrieval mechanisms sharing one encoder) -- a different object entirely, even though the mathematical machinery (error dot product, cosine, D/C identity) is the same. The two are not substitutable, and this track's new PHASE D code will be written as new, separate analysis (not a re-run of `diag_j3_error_complementarity01.py`), reusing only the low-level identity-check pattern, not its object of study.
